# TUI 编辑标题的延迟

2026-10-29, 用户报告使用 `e` 编辑 session 标题后卡住 10 秒以上.

现场只读检查显示 37 条 session 的 JSON 读取约 0.2ms, SQLite 已提交记录读取约 1.3ms.  操作锁被占用, 已打开该锁文件的进程包括通知监控和 TUI.  每个进程各做 1 秒只读采样, 通知监控大量时间等待子进程输出, TUI 的后台同步线程等待文件锁.  没有对宿主 tmux 执行探针、按键或清理.

原后台 `reconcile_all` 持有整个 profile 的 `managed-operation.lock`, 在锁内扫描全部 session 的 tmux pane, 查询进程和 xats 绑定.  前台 `rename_selected` 保存标题前也要拿这把锁, 因而等待整轮扫描.  独立容器中, 37 条无竞争记录的编辑约 62ms; 人为持操作锁 12 秒时, 保存约 12.67 秒.  37 个真实 shell session、每个 4 个 pane, 加上每次 tmux 调用 30ms 的受控开销后, 原版保存约 12.54 秒.

另一条独立路径是列表恢复标记查询使用 `open_with_schema`, 同时做事件清理等维护写操作.  SQLite 写锁使两次 reload 累计阻塞约 9.45 秒.  读取恢复标记不应触发数据库维护.

本轮后台同步改为每个 session 一个短临界区, 取得锁后重新读取其当前元数据, 完整处理后释放.  后台尝试取锁时不等待前台, 忙则后续刷新重试.  前台生命周期操作原有的互斥保护保留.  数据库初始化和维护放在操作锁之外, 后台派生写忙时不持操作锁等待.

扫描期间允许其他元数据操作交错, 因此只有所有中间快照和收尾记录都与起始记录一致时才做 orphan capture 清理.  观察到编辑、新增、删除或目标缺席后, 永久取消本轮清理资格, 即使记录随后恢复原样也不执行, 避免误删未完整观察的 pane 数据.

界面恢复标记改成只读、无锁等待的批量查询, 缺少数据库不创建, 暂不可读保留上次缓存.  已有 WAL 写事务期间只读取已提交记录.  tmux 存活缓存按批刷新, 不再为没有 slot 的 session 检查存活.

项目经验: UI 主线程查询展示缓存时不应顺带执行 schema 或垃圾清理; profile 级互斥锁不应覆盖整轮外部进程及服务查询.  性能验收必须区分打开编辑框、提交保存、JSON 写入和后台锁等待, 并在同一受控环境比较.

产物与来源记录位于 `target/review-builds/20261029-title-latency/`.  实际性能和并发回归由独立 tester 在无网络、无宿主挂载的一次性容器中完成.  不混用不同候选的性能数字.
