# 两个 Codex pane 的会话被互相绑错 (机制已验证, 未修)

记录于 2026-08-01.  机制是**实测确定的**, 不是推测.  **目前不修**, 原因见文末.

## 现象

同一个会话里的两个 codex pane, 各自的 `agent_slot.native_session_id` 记成了**对方的会话**.  后果是按 `R` (resume) 时会把**别人的对话**恢复到这个 pane 里.  `Shift+C` (fresh 重启) 和 xats 自动注册**不受影响** —— 后者认的是 pane + identity key, 与会话 id 无关.

**不会自愈**: 交叉之后两个 pane 都有了 `pane_live` 行, 而重新认领只在"行早于当前进程"时发生, 两个 pane 都没换进程.

## 机制 (实测): 有**两条独立路径**

修好其中任何一条都不覆盖另一条.

### 路径 A — 落盘**顺序**错开 → 必然交叉

```
人为让后启动的 pane 先落盘  → 7 / 7 轮全部交叉
两个都在启动时落盘 (对照)   → 0 / 7 轮交叉
```

两格只差一个 `stub-mode` 参数.  **不是概率事件, 是把变量翻过来就必然发生.**

根因: `find_rollout` 的判据是"时间戳 **≥** 本 pane 进程启动 − 2 秒"的**最早未认领**的那个 —— **只有下界, 没有上界**.  于是只要在两个 rollout 文件之间有一次 reconcile tick, **先被处理的 pane 就会拿走当时唯一存在的那个, 而那是另一个 pane 的**; 之后第二个文件落盘, 剩下那个 pane 拿走它.

时间条件天然满足: **rollout 是延迟落盘的** —— 文件要到该 pane 第一轮对话之后才写出来, 而**文件名保留会话开始时间**.  所以晚落盘的那个在下界筛选上不会被排除.

### 路径 B — 会话开始时刻**并列** → 抛硬币 (这条是生产常态)

```
cross_agent_team 开 (有 bootstrap)  → 6 / 10 轮交叉,  landing gap 全是 0 秒
cross_agent_team 关 (无 bootstrap)  → 0 / 7  轮交叉
```

唯一变量是 bootstrap 的有无.  而 **bootstrap 做的不是"让一个先落盘", 是把两个 pane 的 `exec codex` 都推迟并压进同一秒**:

```
bootstrap 开, 一个交叉轮:  2026-08-01T07-10-54   2026-08-01T07-10-54   ← 同一秒
bootstrap 关, 一个正常轮:  2026-08-01T07-07-05   2026-08-01T07-07-04   ← 差 1 秒
```

时间戳相等之后, `find_rollout` 里是:

```rust
candidates.push((ts, thread_id, entry.path()));
candidates.sort();
```

Rust 元组排序在 `ts` 并列时**按 `thread_id` 字典序决胜**, 而 thread_id 是随机 uuid —— 于是"谁最早"退化成**抛硬币**.  实测 6/10, 与 p≈0.5 一致.  那十轮里唯一 gap=1s 的一轮 (时间戳不并列) 结果是**正确的**, 是自己出现的反向对照.

**为什么这条是生产常态**: 一次 `Shift+C` 扇出两个 pane 是亚秒级的, 加上 bootstrap 的推迟, 两个会话几乎必然落在同一秒.

无 bootstrap 时 `add-agent-pane` 天然把两个 pane 隔开 ≥1 秒, 时间戳不并列, 所以 0/7.

## 用户能做什么

**重启那个 pane.**  重启会让它换进程, 于是 `pane_live` 行相对新进程变陈旧, 认领重新发生 —— 这是目前唯一的自救手段.

## 为什么不修

### 试过并被否掉的判据: "离谁近就归谁"

想法是把"取最早的"换成"候选的时间戳离哪个 pane 的启动时刻更近就归谁".  **被三个反例否掉**:

1. **两个时间量都是秒粒度** —— rollout 文件名按 `%Y-%m-%dT%H-%M-%S` 解析, pane 启动时刻经 `ps -o etime=` → `parse_etime` 也是秒.  实测那七轮里两个 rollout 的**文件名秒数相同**, 两个 pane 也在同一秒内启动 → 四个量落进同一秒 → 比不出来.  **它在它要修的那个场景 (Shift+C 同时起两个 pane) 里恰好没有分辨力**.  这一条后来被路径 B 的数据坐实: 同秒并列**不是边角情形, 是 bootstrap 开着时的默认情形**;
2. 秒边界把亚秒差异变成并列甚至反转;
3. **偏移不是共同项** —— "sh 比 codex 早启动"这个偏差被认为对两个 pane 相等, 因此会在相对比较里抵消.  实测**不相等**: 带 bootstrap 的 pane 多出 `nc` + `npx` 那一段, 秒级且抖动大.  偏移不对称时, 判据**不只是失效, 是会主动判错**.

### 更根本的: aoe 侧不存在真值

实测 pane 侧**没有任何会话句柄**:

- 载体 shim 的环境: 无 `CODEX_THREAD_ID` 一类变量;
- native child 的环境: 同样没有;
- `pane_title`: 是 aoe 自己设的, 不含会话;
- 该载体打开的文件: **没有任何 `$CODEX_HOME/sessions/` 下的 rollout**.

最后一条解释了前三条: **`--remote` 形态下 rollout 是 app-server 写的, 不是 pane 写的**, 所以 pane 手里没有句柄; 而环境是 `exec` 时固定的, 会话是之后才建的.

**所以 aoe 侧任何判据必然是推断, 不可能是查证.**  这不是"没找够", 是没有.

### 根治的杠杆不在这个仓库

**唯一真正持有 pane↔会话映射的是 app-server** (它知道哪条客户端连接对应哪个会话).  要根治, 方向是"**让 app-server 或 codex 把会话 id 暴露给它自己那个 pane**", 而不是在 aoe 里把时间戳猜得更准.

## 如果将来要做, 已知的最佳形态

**延迟认领, 挂在阻塞者的年龄上**:

> 分不出归属时本轮不认领; 但只有当那个"同样近"的竞争 pane **还年轻**时才拒绝 —— 一个已经活了很久还没有 rollout 的 pane **不再构成阻塞**.

为什么挂"阻塞者老化"而不是"受害者等够 N 秒":

- 永不说话的 pane (右 pane 开着当备用, 半小时不打一个字 —— 常见形态) 只在最初一小段时间挡人, 之后系统回到今天的行为;
- 不需要给受害者记时, 状态更少;
- 失效方向更好: "受害者等待"是一个**隐形状态** (谁都不知道它在等), 而"阻塞者老化"在任何时刻都处于可解释的形态.

**必须带这个老化条件**: 不带的话会静默饿死 —— rollout 延迟落盘, 一个从没说过话的 pane 永远不产生文件, 于是永远与兄弟并列、永远被拒绝.  而且那比今天更差: **今天的贪心至少会绑上某个会话 (可能是错的), 一个都不绑意味着那个 pane 连 slot 都进不去 —— 不可重启、不可恢复, 且静默.**

**但它只覆盖路径 A.**  错开量的分布已经测了, 结论不是"阈值取多少", 而是 **路径 B 的 landing gap 全是 0 秒** —— 两个文件早就都在了, 时间戳就是相等的, **没有东西可等**.  延迟认领对路径 B 完全无效.

要一起覆盖, aoe 侧唯一能做的是**并列时不猜** (时间戳相等且有多于一个未绑定 codex pane 时本轮不认领), 但那同样需要"阻塞者老化"补丁, 而且**老化窗口过后仍然要抛硬币** —— 只是把 50% 推迟了, 没有消除.

## 顺带发现: 并列时的决胜是随机的

`find_rollout` 里 `candidates.sort()` 排的是 `(ts, thread_id, path)` 元组, 所以 `ts` 并列时**按 thread_id 字典序决胜**, 而 thread_id 是随机 uuid.  这就是路径 B 表现为 ~50% 而不是稳定错或稳定对的原因.

把决胜改成确定性的 (比如按 pane 顺序) **不会改善正确性** —— 没有任何可用信息说明哪个 rollout 属于哪个 pane —— 只会把一个抛硬币的 bug 变成一个稳定的 bug.  记在这里是为了说明那个 50% 的来源, 不是修法建议.
